# 01 — 第一个像素到窗口

第 00 章给了你能编译、能跑测试的骨架，但屏幕上还没有一个像素。这一章建"像素通路"：**你的代码算出的像素 → 内存 → 窗口**。结束时你手里有四样东西：
一个像素由你写的 Win32 窗口、一个能存能开的 BMP 写出器、一套自绘位图字体、以及一条能背下来的方向约定——后面每一章都站在它上面。
顺序是刻意的：**先定方向，再写像素**；本项目最贵的一类假通过（两次翻转互相抵消、画面看起来完全正确）根源就在这里。

## 1. 为什么是 `CreateDIBSection`，而不是 GDI 画图

**主张：渲染器只写内存，窗口只负责把这块内存 present 上屏。** GDI 的 `SetPixel`/`TextOut` 是"请系统替你画"，每个像素一次系统调用，
颜色管线不受你控制。`CreateDIBSection` 反过来：让 GDI 分配内存并把指针交给你（`src/app/dib.cpp:42-44`），你写 `uint32_t`，
每帧一次 `BitBlt` 整块搬上窗口 DC（`src/app/win32_window.cpp:119`）。代价：每帧一次 blit；回报：屏幕上每个像素都经过你的代码——后面一切 golden 回归的前提。

像素布局由格式定死：32bpp DIB 的内存字节序是 **B,G,R,A**，按小端读成 `uint32_t` 值是 `0xAARRGGBB`（`src/render/color.h:15-16`）。名字说的是字节序，值说的是读出来的数，
写反的症状是红蓝互换；`tests/unit/test_color.cpp:67-86` 两条测试钉住它。片段里 `reinterpret_cast<uint32_t*>(bits)` 不踩严格别名：那是 GDI 分配的原始存储，上面还没有任何别的类型的对象，
当 `uint32_t` 数组用正是它的用途（真正踩线的是"拿已存在的 `float` 数组当 `int` 读"那种）。离屏面对 `vector<uint8_t>` 同样这么做（`src/app/surface.cpp:20`），像素缓冲的通用写法，两大编译器都按预期工作。

## 2. 最小片段 1：窗口 + DIB + 渐变

存成 `snippet_window.cpp`，两条工具链都能编（命令在文件头两行）。画一条左蓝右红的水平渐变，跑 120 帧自关：

```cpp
// cl /EHsc /std:c++20 /W4 snippet_window.cpp user32.lib gdi32.lib
// g++ -std=c++20 -Wall -Wextra snippet_window.cpp -luser32 -lgdi32
#ifndef WIN32_LEAN_AND_MEAN
#define WIN32_LEAN_AND_MEAN
#endif
#ifndef NOMINMAX
#define NOMINMAX   // 否则 windows.h 的 min/max 宏会毁掉 std::min/std::max
#endif
#include <windows.h>
#include <cmath>
#include <cstdint>
#include <cstdio>

namespace {
constexpr int kW = 640, kH = 360;
// IEC 61966-2-1：线性 → sRGB 字节（与 src/render/color.cpp 同一条曲线）
uint8_t encode(float v) {
    const float s = (v <= 0.0031308f) ? 12.92f * v : 1.055f * std::pow(v, 1.0f / 2.4f) - 0.055f;
    return static_cast<uint8_t>(s * 255.0f + 0.5f);
}
LRESULT CALLBACK onMessage(HWND hwnd, UINT msg, WPARAM wp, LPARAM lp) {
    if (msg == WM_CLOSE || (msg == WM_KEYDOWN && wp == VK_ESCAPE)) { DestroyWindow(hwnd); return 0; }
    if (msg == WM_DESTROY) { PostQuitMessage(0); return 0; }
    return DefWindowProcW(hwnd, msg, wp, lp);
}
}  // namespace

int main() {
    std::printf("encode(0.5) = %d\n", static_cast<int>(encode(0.5f)));   // 188，不是 128
    WNDCLASSW wc{};
    wc.lpfnWndProc = onMessage;  wc.hInstance = GetModuleHandleW(nullptr);  wc.lpszClassName = L"Guide01Window";
    if (RegisterClassW(&wc) == 0) return 1;
    // 没有 WS_THICKFRAME ⇒ 不可拖拽缩放；AdjustWindowRect 保证**客户区**是 kW×kH
    const DWORD style = WS_OVERLAPPED | WS_CAPTION | WS_SYSMENU | WS_MINIMIZEBOX;
    RECT r{0, 0, kW, kH};
    AdjustWindowRect(&r, style, FALSE);
    HWND hwnd = CreateWindowExW(0, wc.lpszClassName, L"guide-01", style, CW_USEDEFAULT,
                                CW_USEDEFAULT, r.right - r.left, r.bottom - r.top, nullptr,
                                nullptr, wc.hInstance, nullptr);
    if (hwnd == nullptr) return 1;
    ShowWindow(hwnd, SW_SHOW);
    // 32bpp BI_RGB 没有调色板：header + 一点余量就够（声明整张 BITMAPINFO = 16KB 栈数组）
    struct DibInfo { BITMAPINFOHEADER header; RGBQUAD spare[3]; } info{};
    info.header.biSize = sizeof(BITMAPINFOHEADER);
    info.header.biWidth = kW;  info.header.biHeight = -kH;   // 负值 ⇒ top-down：行 0 是上边缘（C8）
    info.header.biPlanes = 1;  info.header.biBitCount = 32;  info.header.biCompression = BI_RGB;
    void* bits = nullptr;  HDC wndDc = GetDC(hwnd);
    HBITMAP dib = CreateDIBSection(wndDc, reinterpret_cast<BITMAPINFO*>(&info), DIB_RGB_COLORS,
                                   &bits, nullptr, 0);
    if (dib == nullptr || bits == nullptr) return 1;
    HDC memDc = CreateCompatibleDC(wndDc);
    // 必须把 DIB 选进 memory DC：否则 BitBlt 的源是兼容 DC 自带的 1×1 默认位图，而它照样返回成功
    HBITMAP old = static_cast<HBITMAP>(SelectObject(memDc, dib));
    uint32_t* px = reinterpret_cast<uint32_t*>(bits);   // 字节序 B,G,R,A ⇒ 值 0xAARRGGBB
    bool running = true;
    for (int frames = 0; running && frames < 120; ++frames) {   // 冒烟自关：120 帧后退出
        MSG m{};
        while (PeekMessageW(&m, nullptr, 0, 0, PM_REMOVE)) {
            if (m.message == WM_QUIT) running = false;
            TranslateMessage(&m);
            DispatchMessageW(&m);
        }
        for (int y = 0; y < kH; ++y)   // 渐变在**线性**空间算，只在写像素那一刻编码成 sRGB 字节
            for (int x = 0; x < kW; ++x) {
                const float t = static_cast<float>(x) / static_cast<float>(kW - 1);
                px[y * kW + x] = 0xFF000000u | (static_cast<uint32_t>(encode(t)) << 16) | encode(1.0f - t);
            }
        BitBlt(wndDc, 0, 0, kW, kH, memDc, 0, 0, SRCCOPY);
        Sleep(1);
    }
    SelectObject(memDc, old);   // 先换回旧位图再删，否则 DeleteObject 失败（泄漏）
    DeleteObject(dib);  DeleteDC(memDc);  ReleaseDC(hwnd, wndDc);  DestroyWindow(hwnd);
    return 0;
}
```

盯住三处：`biHeight = -kH`（负值 ⇒ top-down，这就是 C8）；DIB 必须 `SelectObject` 进 memory DC；渐变在线性空间算、写像素那一刻才编码——`encode(0.5)` 打印 **188** 而不是 128，§5.3 解释为什么。

## 3. 最小片段 2：一个能打开的 BMP

BMP 是 24bpp、行自底向上、每行补到 4 的倍数。为什么是 BMP 不是 PNG：PNG 编码要 deflate，那是渲染之外的一整块工作（设计文档 C2/N5，`src/loader/bmp_writer.h:12-13`）。存成 `snippet_bmp.cpp` 编译运行，产出 `guide01.bmp`（4×2，上红下蓝，78 字节）：

```cpp
// cl /EHsc /std:c++20 /W4 snippet_bmp.cpp
// g++ -std=c++20 -Wall -Wextra snippet_bmp.cpp
#include <cstdint>
#include <cstdio>
#include <fstream>
#include <vector>

int main() {
    constexpr int W = 4, H = 2;
    // 源像素 top-down（C8）：行 0 = 上边缘（红），行 1 = 下边缘（蓝）
    const uint32_t src[H][W] = {
        {0xFFFF0000u, 0xFFFF0000u, 0xFFFF0000u, 0xFFFF0000u},
        {0xFF0000FFu, 0xFF0000FFu, 0xFF0000FFu, 0xFF0000FFu},
    };
    const uint32_t rowBytes = static_cast<uint32_t>(W) * 3u;
    const uint32_t stride = (rowBytes + 3u) & ~3u;   // 每行补到 4 的倍数
    const uint32_t imageSize = stride * static_cast<uint32_t>(H);
    const uint32_t fileSize = 54u + imageSize;
    std::vector<uint8_t> out;
    out.reserve(fileSize);
    auto put16 = [&](uint16_t v) {
        out.push_back(static_cast<uint8_t>(v & 0xFF));
        out.push_back(static_cast<uint8_t>((v >> 8) & 0xFF));
    };
    auto put32 = [&](uint32_t v) {
        for (int i = 0; i < 4; ++i) out.push_back(static_cast<uint8_t>((v >> (8 * i)) & 0xFF));
    };
    out.push_back('B'); out.push_back('M');   // BITMAPFILEHEADER (14)
    put32(fileSize); put32(0); put32(54);
    put32(40);                                 // BITMAPINFOHEADER (40)
    put32(static_cast<uint32_t>(W));
    put32(static_cast<uint32_t>(H));           // 正值 ⇒ 文件行序自底向上
    put16(1); put16(24);                       // planes / bpp
    put32(0); put32(imageSize);                // BI_RGB / 数据段大小
    put32(2835); put32(2835);                  // 2835 像素/米 = 72 DPI：打印用，不参与像素解码（见下文）
    put32(0); put32(0);
    // 像素：全文件唯一一次行序转换 —— y 从 H-1 递减到 0
    for (int y = H - 1; y >= 0; --y) {
        for (int x = 0; x < W; ++x) {
            const uint32_t p = src[y][x];
            out.push_back(static_cast<uint8_t>(p & 0xFF));          // B
            out.push_back(static_cast<uint8_t>((p >> 8) & 0xFF));   // G
            out.push_back(static_cast<uint8_t>((p >> 16) & 0xFF));  // R
        }
        for (uint32_t i = rowBytes; i < stride; ++i) out.push_back(0);   // 行尾 padding
    }
    // 先拼完整帧、最后才开文件：参数错时不会把已存在的同名文件截成 0 字节
    std::ofstream f("guide01.bmp", std::ios::binary | std::ios::trunc);
    if (!f) { std::puts("cannot open guide01.bmp"); return 1; }
    f.write(reinterpret_cast<const char*>(out.data()), static_cast<std::streamsize>(out.size()));
    f.close();
    std::printf("guide01.bmp %u bytes\n", fileSize);
    return f ? 0 : 1;
}
```

全文件唯一一次行序转换就是 `y` 从 `H-1` 递减到 `0` 那个循环：源像素 top-down（行 0 = 红 = 上边缘），文件第一行数据必须是图像**底**边（蓝）。4×2 的行宽 12 字节恰好已对齐，
padding 循环没干活；换成宽 5 就要补 1 字节（生产版对应测试用 5×3，断言文件 102 字节，`tests/unit/test_bmp.cpp:54-76`）。DPI 那两个字段是打印分辨率（像素/米），**不参与像素解码**：
实测把本片段产物的 DPI 改成 0，Windows GDI 的 `LoadImage` 照样读出逐像素相同的图（上红下蓝）；第 03 章的最小写出器就留 0，同样能打开。生产版写 2835 像素/米，即 **72 DPI**（`src/loader/bmp_writer.cpp:15-17`；旧注释曾误称 96，已更正），两种写法都不影响解码。

## 4. 最小片段 3：自绘位图字体

HUD 的文字也要由你算出来。这个片段把 8×8 字模画进 `uint32_t* + stride` 的裸缓冲（零项目依赖）再写一张 BMP；字形与生产表逐格相同，只列了用到的字符。存成 `snippet_font.cpp` 编译运行：

```cpp
// cl /EHsc /std:c++20 /W4 snippet_font.cpp
// g++ -std=c++20 -Wall -Wextra snippet_font.cpp
#include <cstdint>
#include <cstdio>
#include <fstream>
#include <vector>

// 5 列 × 7 行字形 + 1 空行行距，'#' 是前景（字形与生产表逐格相同）。
// 这里只列 "HELLO 01" 用到的字符；生产版是 ASCII 32..95 全表（src/render/overlay_font.cpp）。
const char* glyphFor(char c) {
    if (c >= 'a' && c <= 'z') c = static_cast<char>(c - 'a' + 'A');   // 小写映射大写
    switch (c) {
        case 'H': return "#...#" "#...#" "#...#" "#####" "#...#" "#...#" "#...#" ".....";
        case 'E': return "#####" "#...." "#...." "#####" "#...." "#...." "#####" ".....";
        case 'L': return "#...." "#...." "#...." "#...." "#...." "#...." "#####" ".....";
        case 'O': return ".###." "#...#" "#...#" "#...#" "#...#" "#...#" ".###." ".....";
        case '0': return ".###." "#...#" "#..##" "#.#.#" "##..#" "#...#" ".###." ".....";
        case '1': return "..#.." ".##.." "..#.." "..#.." "..#.." "..#.." ".###." ".....";
        case ' ': return "....." "....." "....." "....." "....." "....." "....." ".....";
        default:  return "#####" "#...#" "#...#" "#...#" "#...#" "#...#" "#####" ".....";   // 缺字 = 方块，必须看得见
    }
}

int main() {
    constexpr int W = 64, H = 16;
    constexpr int pitch = W * 4 + 16;   // 故意不连续的 stride：行跨度写错立刻暴露（M0 notes §1）
    std::vector<uint8_t> mem(static_cast<size_t>(pitch) * H, 0);
    auto px = reinterpret_cast<uint32_t*>(mem.data());
    for (int y = 0; y < H; ++y)
        for (int x = 0; x < W; ++x) px[y * (pitch / 4) + x] = 0xFF101418u;   // 背景
    int penX = 4;
    for (const char* s = "HELLO 01"; *s != '\0'; ++s) {
        const char* g = glyphFor(*s);
        for (int row = 0; row < 8; ++row)
            for (int col = 0; col < 5; ++col)
                if (g[row * 5 + col] == '#') px[(4 + row) * (pitch / 4) + penX + col] = 0xFFFFFFFFu;
        penX += 6;   // 5 列字形 + 1 列间距 = 生产版的 kGlyphAdvancePx
    }
    // 写 BMP（24bpp 自底向上，与片段 2 同理；寻址必须按 pitch 而不是 W*4）
    const uint32_t rowBytes = static_cast<uint32_t>(W) * 3u, stride = (rowBytes + 3u) & ~3u;
    const uint32_t fileSize = 54u + stride * static_cast<uint32_t>(H);
    std::vector<uint8_t> out;
    auto put32 = [&](uint32_t v) { for (int i = 0; i < 4; ++i) out.push_back(uint8_t((v >> (8 * i)) & 0xFF)); };
    auto put16 = [&](uint16_t v) { out.push_back(uint8_t(v & 0xFF)); out.push_back(uint8_t(v >> 8)); };
    out.push_back('B'); out.push_back('M');
    put32(fileSize); put32(0); put32(54);
    put32(40); put32(static_cast<uint32_t>(W)); put32(static_cast<uint32_t>(H));
    put16(1); put16(24); put32(0); put32(stride * static_cast<uint32_t>(H));
    put32(2835); put32(2835); put32(0); put32(0);
    for (int y = H - 1; y >= 0; --y) {
        const uint32_t* row = px + static_cast<size_t>(y) * (pitch / 4);
        for (int x = 0; x < W; ++x) {
            out.push_back(uint8_t(row[x] & 0xFF));
            out.push_back(uint8_t((row[x] >> 8) & 0xFF));
            out.push_back(uint8_t((row[x] >> 16) & 0xFF));
        }
        for (uint32_t i = rowBytes; i < stride; ++i) out.push_back(0);
    }
    std::ofstream f("font01.bmp", std::ios::binary | std::ios::trunc);
    if (!f) { std::puts("cannot open font01.bmp"); return 1; }
    f.write(reinterpret_cast<const char*>(out.data()), static_cast<std::streamsize>(out.size()));
    f.close();
    std::printf("font01.bmp %u bytes\n", fileSize);
    return f ? 0 : 1;
}
```

产出 `font01.bmp`（3126 字节）：深色底上一行白色 `HELLO 01`，字符间有一列空隙。缓冲故意用 `pitch = W*4 + 16`：行跨度错写成 `W*4` 的话第一行之后整幅字立刻错位——这正是生产测试夹具用不连续 pitch 的理由（`tests/unit/test_render_target.cpp:12-13`）。

## 5. 指回本仓库：生产版本多了什么、为什么多

### 5.1 C4：`<windows.h>` 只在 `src/app/`

设计文档 C4（`docs/superpowers/specs/2026-11-21-soft-raster-design.md:90-91`）：核心库不得出现 Win32 符号，framebuffer 只接收 `uint32_t*` + 宽高/步长。
回报是可测试性：测试目标只链 `soft_raster_core + soft_raster_loader`（`CMakeLists.txt:148`），从不链 app；app 才是链它们的那个（`CMakeLists.txt:175-178`）。
自检一条 grep（M0 notes §8）：`grep -rn "#include <windows" src/ | grep -v '^src/app'`，期望无输出（HEAD 上实测无输出）。
注意"目录 ≠ target"：`bmp_writer.cpp` 住在 `src/loader/` 却属于 core（`CMakeLists.txt:27`）；反过来，`cmdline/scene/view_mode` 三个不含 Win32 的 app TU 被直接编进测试目标（`CMakeLists.txt:140-145`）。两个真坑，都以链接错误收场：

- **宏撞名**。WinUser.h 有 `#define DrawState DrawStateA`，项目的 `DrawState` 类型在 core 一切正常，一进 app 就被静默改名——链接错误里出现源码中根本不存在的 `sr::DrawStateA`。
  类型后来改名 `PipelineState`，并在头文件顶部加 `#ifdef … #error` 守卫（`src/render/pipeline.h:15-29`），把"疯狂的链接错误"变成"一行编译错误"。
- **`NOMINMAX` / `WIN32_LEAN_AND_MEAN`**。没有 `NOMINMAX`，windows.h 的 min/max 宏会把 `std::min(best, v)` 解析成成员访问，报错是看不懂的 C2589（`src/app/main.cpp:10-19`）。项目里每个包含 windows.h 的 TU 都先定义这两个宏。

### 5.2 Surface：工厂返回 `unique_ptr`，构造函数不公开

生产版把"像素的出口"抽象成 `Surface`：窗口（DIB+BitBlt）与离屏（堆内存）两种实现，渲染只认识 `RenderTarget`，golden 与 `--bench` 没有窗口也能渲整帧（`src/app/surface.h:11-15`）。
构造函数 protected、禁拷贝禁移动、工厂一律返回 `unique_ptr`（`src/app/surface.h:20-50`、`src/app/surface.cpp:93-102`）。理由是一个真 bug：第一版夹具**按值返回**含内部裸指针的结构体，
返回那一刻指针悬垂，MSVC Debug CRT 弹出没人能点的模态对话框，进程永久挂住、CTest 报 Timeout——症状像死循环，实际是内存错误（M0 notes §7(b)，`src/app/surface.h:17-19`）。
生产版还多两条自检：DIB 选进 memory DC 后确认 DC 里当前位图就是它（`src/app/surface.cpp:47-56`，忘选的话 BitBlt blit 的是 1×1 默认位图，这个 bug 逃过了当时全部测试——离屏根本不碰 DIB）；
析构前显式 deselect（`src/app/surface.cpp:79-81`，否则 `DeleteObject` 失败泄漏）。

### 5.3 单一编码点，以及那个 188

**主张：`encodeSRGB` 全栈恰好出现一次——写颜色目标那一刻**（`src/render/render_backend.cpp:117`；测试图案同样，`src/render/patterns.cpp:21`）。光照（点积、相加、乘系数）全在线性空间做（设计文档 §7.1，`src/render/color.h:7-9`）。
两种失败症状可以算出来：解码是压缩，0.5 解一次得 0.2140、解两次得 0.0376——暗部死黑；编码是膨胀，0.5 编一次得 0.7354（字节 188）、编两次得 0.8732（字节 223）——整体发白。
生产实现走 12bit 输入域的 LUT（4096 项，`src/render/color.cpp:8`）而不是 256 项：256 项表等于量化两次，暗部 2–3 LSB 偏差，平滑渐变上是可见的带状条纹（M0 notes §4）。

188 是 M6.5 实测的 wart：法线视图输出 `(N+1)/2`（线性域），出口恒定编码，于是 N=(0,0,1) 的像素是 (188,188,255)，画面是粉彩的。188 来自 IEC 分段曲线：
0.5 高于接缝 0.0031308，走幂段 `1.055·0.5^(1/2.4) − 0.055 ≈ 0.7354`，×255 = 187.5 ⇒ lround = **188**（曲线 `src/render/color.cpp:10-14`，取整 `:34`；`docs/notes/M6-光照与休眠接口.md:195-203`）。
这是单一编码点的**正确后果**，不是 bug；也**不是** `Texture::srgb=false` 那件事——那个管输入侧（采样时纹素解不解码），两件事别混。

### 5.4 字体的生产版：度量、ASCII 边界、为什么包进 ColorTarget

片段 3 就是生产 `drawText` 的骨架。不用 GDI `TextOut`：屏幕上不该出现一个不是我们算出来的像素，且文字要在离屏渲染与 golden 里出现，而 GDI 字体需要 DC（`src/render/overlay_font.h:10-17`）。
字形表用字符画而不是十六进制位表：位表错一个 bit 没人看得出，字符画错一个 '#' 一眼看得出（`overlay_font.cpp:10-12`）。生产版多三样东西：

- **度量常量** `kGlyphWidthPx=5`、`kGlyphHeightPx=8`、`kGlyphAdvancePx=6`（`src/render/overlay_font.h:20-22`）。不只用来画字：锚 3 的 HUD 排除矩形由它们推出——
  文字从 (3,3) 起、17 字符 × 6 = 102 宽、8 高，取 `x<110 && y<12` 恰好罩住（`tests/unit/test_obj_golden.cpp:209-215`，`src/loader/obj_scene.cpp:41`）。
- **包进 `ColorTarget`**：`drawText` 只依赖这个非拥有视图，于是能被单测直接断言（`overlay_font.h:14-15`），且越界写被静默丢弃——长错误行在右缘截断而不会写坏内存
  （`render_target.h:22`，`src/app/main.cpp:222`）。你的裸缓冲版没有这层保护，画越界就是踩内存；这是生产版包一层的直接回报。
- **ASCII 边界**：字体只有 ASCII 32..95（小写映射大写），其余字符画方块——缺字必须看得见，静默画空白的话 HUD 少一整段你也不会发现（`overlay_font.cpp:104-111`）。
  于是中文错误原因在屏幕上是一排方块，而中文路径场景恰恰是屏幕最该读到信息的地方。解法是 `hudAscii`：非 ASCII 字节转义成 `\xHH` 上屏，终端保留完整 UTF-8（`src/app/main.cpp:100-121`）。
  背后原则：**该看到什么必须 always 在画面上**，"细节进终端"不满足它。不加中文字体——那是与渲染无关的一整块工作。

### 5.5 帧循环：节流与暂停

**按帧预算节流，而不是固定 `Sleep(1)`。** 生产帧循环在 `src/app/main.cpp:397-537`。固定 Sleep(1) 让动画看起来"不丝滑"——不是慢，是抖：Windows 的 Sleep 粒度约 1–15ms，每帧耗时被随机拉长。
现在用 `lapMs()` 结算一帧总耗时，`remaining = frameBudgetMs - elapsed`，剩多于 1ms 才睡，睡不够就不睡（宁可掉一帧也不累积延迟，`src/app/main.cpp:515-517,530-536`）。
`lapMs()` 读一次时钟并重置，一帧只有一个 dt（`src/bench/timer.h:29-34`）。默认窗口 1280×720、不可缩放（`src/app/cmdline.h:17-18`，设计文档 §10.8）：
深度缓冲在 Surface 创建时一次分配（`src/app/surface.cpp:19,60`），窗口尺寸不变就不需要重分配。tile 网格则是留给 M8 的接口——Backend A 目前每个三角形传的是空 `TileGrid{}`
（`src/render/render_backend.cpp:64`），`TileGrid::forTarget` 只有测试在调（`tests/unit/test_triangle_setup.cpp:218,238`）。

**暂停 = 画面必须不变（C7）。** `shouldRender = !paused || input.stepFrame`（`main.cpp:476`）：暂停时输入仍泵（否则系统认为没响应），但不重渲，只 present 旧帧（`main.cpp:510-513`）。
一个能从代码直接推出的后果：`V`（视图循环）在渲染门**之前**处理（`main.cpp:404-413`），所以暂停时按 V 会改视图状态、终端打印 `[view] …`，画面却不动——
要按 O 单步或 P 恢复才看到新视图。这是"暂停即冻结"的代价，不是 bug，但你必须知道，否则会以为视图切换坏了。

## 6. 坑（一手来自 docs/notes/）

### 6.1 翻转点全清单，与"两个错误互相抵消"

C8（设计文档 `2026-11-21-soft-raster-design.md:96-98`）：core 的颜色与深度输出**一律 top-down**，行 0 是上边缘；DIB 的 bottom-up 转换只发生在 `src/app/dib.*`——
而生产版用负 `biHeight` 让它**根本不发生**（`src/app/dib.cpp:37`）。为什么这么严：窗口显示与 golden BMP 必须**按构造**一致，Viewport 阶段完全不知道 DIB 存在。
反面做法（正 biHeight + 写 DIB 手动翻行）多一个翻转点，而它颠倒起来与 golden 的颠倒一模一样，你无法从画面区分是谁翻了（M0 notes §2）。成品项目里翻转点的全清单（各管各的格式，互不叠加）：

| 位置 | 格式约定 | 翻译 |
|---|---|---|
| BMP 写出器 | 行自底向上 | 翻一次，y 递减（`src/loader/bmp_writer.cpp:91`） |
| DIB | 正 biHeight 即 bottom-up | 负 biHeight ⇒ 不翻（`src/app/dib.cpp:37`） |
| TGA 载入 | header bit5 定 origin | bit5=0 时翻行（`src/loader/image_tga.cpp:120-125`） |
| stb（PNG/JPG） | 总是 top-down | 显式 `stbi_set_flip_vertically_on_load(0)`（`src/loader/image_stb.cpp:80-82`） |
| OBJ `vt` | v=0 是图片下边缘 | 解析器出口一次 `v = 1 - v`（`src/loader/obj.cpp:54-59`） |

OBJ 那一次由契约指派给载入器："图像第 0 行 = 顶部、采样器 v=0 = 第 0 行、mesh 的 v=0 = 这一面的顶边 ⇒ 贴图与图像同向；
OBJ 的 vt 原点在左下，那一次 `v = 1 - v` 由 M5 的载入器负责"（`src/scene/mesh.cpp:51-54`）。格式的差异在格式的门口处理掉，不留进管线。

M5 的教训：**两次翻转可以互相抵消**。obj 忘翻、tga 也忘翻，合成画面看起来完全正确。实测修订（M5.7 变异③）：抵消在 level-0 双线性路径上精确
（两帧 md5 相同），mip 生成也精确（int 累加与翻行可交换），残差只来自三线性采样——3 个 ±1 像素。于是判别分三档：±1 容差门禁完全放过抵消；
零容差锚会红，但抓它的是舍入噪声不是语义，换编译器可能消失；**真正抓抵消的是两条语义锚**（OBJ 解析 vs 程序生成 cube、TGA 解码 vs 程序生成 checker），
每条翻转各养一条独立的锚，少任何一条都不算过（M5 notes §1）。

### 6.2 BMP：顺序是接口的一部分；路径用 `fs::path`

**先校验、再在内存拼完整帧、最后才开文件**（`src/loader/bmp_writer.cpp:40-55`）。反过来做，一次失败的截图会把已存在的同名文件截成 0 字节——
golden 比对失败时看起来像"渲染回归"，实际是上一次截图把自己删了（M0 notes §5）。`pitch != width*4` 直接拒绝而不是内部重排（`bmp_writer.cpp:52-55`，`tests/unit/test_bmp.cpp:142-150`）。

路径参数是 `std::filesystem::path` 而不是 `std::string`（`src/loader/bmp_writer.h:19-22`）：MSVC 的 `ofstream(fs::path)` 走宽字符打开，中文目录能写；窄字符串会被按 ANSI 码页误解码。
错误消息里不能用 `path.string()`——MSVC 上它按 ANSI 码页转换，路径含码页表示不了的字符（英文 locale 机器上的中文目录）时**直接抛 system_error**，而载入器的契约是"返回 false + err"；
未捕获异常触发 debug CRT 的 abort 对话框，整条 ctest 无声挂死。所以消息一律走 `displayPath`（内部 `u8string`，无损 UTF-8，`src/loader/lex.h:80-89`）。

### 6.3 另外两个真 bug（M0 notes §7）

- **`CreateWindowExW` 失败，错误码 1400**。`WM_NCCREATE` 时成员 `m_hwnd` 还没赋值（它等 CreateWindowExW 返回才写），拿它调 `DefWindowProcW` 就是拿 NULL 当句柄。教训：WndProc 全程用消息自带的 `hwnd`（`src/app/win32_window.h:59-61`、`win32_window.cpp:138-146`）。
- **"拖动一卡一卡"**。InputState 每帧清零是对的（位移必须重置），但"左键还按着"是跨帧状态，跟着清零就只有按下那一帧算拖拽，之后自动旋转接管。修法是持续状态单独成类型 `MouseButtons`，每帧开始播种进快照（`src/app/input.h:9-15`，`tests/unit/test_input.cpp:12-32`）。
