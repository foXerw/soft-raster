## 这一章要解决什么问题

没有上一章。这一章回答：**写第一个像素之前，什么必须先定下来？** 结构（谁允许知道什么）、工具链（谁有权判定正确）、

### 形状：方案 3 的管线 + 方案 1 的目录

设计文档 §6 对比过三个方案：单文件渐进式被排除——无法加多线程/SIMD；经典分层 mini-engine 起步最快，
但 shading 与光栅循环耦合，到性能里程碑必须拆开重写。选定"**3+1 混合**"（设计文档 :117-120）：
显式阶段管线（VS → clip → 投影 → 视口 → Setup → Rasterize → FS → sink）的形态，配 math/render/loader/app
分层的目录——M8 的 tile 并行、M9 的 SIMD 都是"加一个后端"，不是"推翻重来"。四个目标，依赖**单向**：
app 与 tests 各自链 loader + core（`CMakeLists.txt:178`、`:148`），loader PUBLIC 链 core（`:74`）；core 不知道上层存在。

### 目录 ≠ target

`src/loader/bmp_writer.cpp` 住在 `src/loader/`，却列在 **core** 的源文件列表（`CMakeLists.txt:27`）；
同目录的 `image_stb.cpp` 才属于 loader（`:69`）。**"文件在哪个目录"不回答"它链不链 stb"，只有 CMake 的源文件列表回答。**
分界是像素从哪进来：BMP/TGA 写出、OBJ/MTL 文本解析是纯数据变换，进 core；PNG/JPG 解码需要 stb，进 loader；
`third_party/` 的 include 路径只对 loader 开放（`:76`）——core 连那个头都搜不到。
C2 的守卫是**文本的**：`grep -rn "stb_image" src/` 只许命中 `src/loader/image_stb.*`。它咬过人：
M5.1 给 `mtl.h` 写的初版注释里出现字面量 `stb_image`，grep **当场**多命中一处（M5 笔记 §3）；
修法是让注释绕开字面量（今天的 `src/loader/mtl.h:7-8`），不是放宽 grep。推论：
**"core 不知道像素"不能写在注释里，只能写在代码结构里**——注释给人读，grep 给机器读，撞车时机器赢。
也别把 grep 当证明：它是绊线不是正确性证明（M6 账本 Ruling 85；账本在 `.superpowers/`，不入 git）。C4 自检刻意 grep `#include <windows`
而不是 `windows.h`：后者命中注释字样，总报噪声的检查最终会被跳过（M0 笔记 §8）。

## 最小片段：一个自注册测试 harness

新建目录 `sr-mini/`，放入下面五个文件。环境：`cl` 不在普通 shell 的 PATH，先 call
`C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat`；g++ 用 `/c/msys64/ucrt64/bin/g++.exe`（M0 笔记 §8）。

```cpp
#pragma once
// 极简自注册 harness。生产版是 tests/harness.h + harness.cpp，机制完全相同。
#include <cmath>
#include <cstdio>
#include <utility>
#include <vector>
namespace srtest {
using Fn = void (*)();
// inline + 函数内 static：跨翻译单元唯一实例，第一次调用时才构造——
// Register 的静态初始化在 main 之前，但 suite() 到被调用才构造，顺序安全。
inline std::vector<std::pair<const char*, Fn>>& suite() {
    static std::vector<std::pair<const char*, Fn>> s;
    return s;
}
struct Register { Register(const char* n, Fn f) { suite().emplace_back(n, f); } };
inline int currentFailures = 0;   // C++17 inline 变量：跨翻译单元唯一
// 比较必须经过函数：if (1+1==2) 这种常量条件在 MSVC /W4 下触发 C4127。
inline bool condIsFalse(bool v) { return !v; }
inline bool nearDiffers(double a, double b, double t) { return !(std::fabs(a - b) <= t); }
inline void fail(const char* file, int line, const char* expr) {
    ++currentFailures;
    std::printf("    FAIL %s:%d  %s\n", file, line, expr);
    std::fflush(stdout);   // 重定向时全缓冲；失败后紧接着崩溃，FAIL 行会随进程消失
}
inline int runAll() {
    std::printf("[run] %d 个用例\n", static_cast<int>(suite().size()));
    int failedCases = 0;
    for (const auto& e : suite()) {
        currentFailures = 0;
        e.second();
        if (currentFailures != 0) { ++failedCases; std::printf("FAIL %s\n", e.first); }
    }
    std::printf("[done] %d 个用例，失败 %d 个\n", static_cast<int>(suite().size()), failedCases);
    return failedCases;
}
}  // namespace srtest
// 自注册的核心：静态对象的构造函数在 main 之前运行，把用例塞进 suite()。
#define SR_TEST(name)                                                    \
    static void name();                                                  \
    static const ::srtest::Register srtest_reg_##name(#name, &name);     \
    static void name()
#define SR_ASSERT(cond)                                                  \
    do { if (::srtest::condIsFalse(static_cast<bool>(cond)))             \
        ::srtest::fail(__FILE__, __LINE__, #cond); } while (0)
// 数值断言一律容差（C1′）：g++ 与 MSVC 的标准库数学不保证逐位一致。
#define SR_ASSERT_NEAR(a, b, tol)                                        \
    do { const double sr_a_ = (a), sr_b_ = (b), sr_t_ = (tol);           \
        if (::srtest::nearDiffers(sr_a_, sr_b_, sr_t_))                  \
            ::srtest::fail(__FILE__, __LINE__, #a " ~= " #b); } while (0)
```

三个值得停下来的 C++ 点：**(1) 静态初始化自注册**——`SR_TEST(foo){...}` 展开成前向声明、静态 `Register`
对象、函数定义三样；静态对象的构造在 `main` 之前运行，"写下用例"与"登记用例"是同一个动作，没有中央列表要维护。
代价在坑 3：这些对象全是内部链接，没人"引用"它们。**(2) 函数内 static 解决初始化顺序**——普通全局 vector
可能晚于别的 TU 里的 `Register` 构造（跨 TU 静态初始化顺序未定义）；包进函数、首次调用才构造，顺序必然安全，
`inline` 保证多 TU 包含时实例唯一。**(3) 比较走 inline 函数**——常量条件在 MSVC /W4 下报 C4127，而构建输出
必须干净：一旦允许噪声，真正的新警告就看不见了（生产版同理由：`tests/harness.h:56-61`）。

其余三个文件（test_smoke.cpp、main.cpp、buildinfo.h）：

```cpp
#include "harness.h"
SR_TEST(harness_detects_a_passing_assert) { SR_ASSERT(1 + 1 == 2); }
SR_TEST(near_tolerance_is_inclusive) { SR_ASSERT_NEAR(1.0f, 1.000001f, 1e-5f); }
// 0.1 + 0.2 == 0.3 在 IEEE 754 下是假的（差约 5.5e-17）——所以数值断言必须是容差。
SR_TEST(floating_point_needs_tolerance) { SR_ASSERT_NEAR(0.1 + 0.2, 0.3, 1e-9); }
```

```cpp

#include "buildinfo.h"
#include "harness.h"
int main() {
    std::printf("soft-raster-mini %s %s %s\n", SR_VERSION, SR_BUILD_CONFIG,
                sr::compilerName());
    const int failed = srtest::runAll();
    // POSIX 把退出码截断到 0–255：恰好 256 条失败会退出 0（看起来全绿）。夹到 1。

}
```

## 指回本仓库：生产版本多了什么、为什么多

### 两条工具链，为什么都活着

MSVC 是主路径，也是**唯一有权判定 golden 图像**的一侧；g++ 侧只要求 core/loader/tests 能配置、能编译、
纯逻辑单测全绿（C1′，设计文档 :77-84）。这不是偷懒，是诚实：libstdc++ 的 `sin/cos/pow/log2` 与 MSVC CRT
**不保证逐位一致**；GCC 默认 `-ffp-contract=fast` 把乘加融合成 FMA 而 MSVC 不融合——同一个式子两边算出不同的位。
为逐位稳定自建三角函数/pow 是计划外的一大块，且与学渲染无关。于是三层让步：GCC 构建加 `-ffp-contract=off`
（`CMakeLists.txt:58-61`）；数值断言一律容差（`tests/harness.h:12-13`，默认 1e-5 量级）；golden 只在 MSVC 判定、
容差 ±1/255/通道（设计文档 §7.8，M3 笔记 §6）。本机 g++ 配置命令（README :26-30；M0 笔记 §8 记录已验证到零警告+全绿）：

```bash
cmake -S . -B build-gcc -G "MSYS Makefiles" \
  -DCMAKE_MAKE_PROGRAM=/c/msys64/usr/bin/make.exe \
  -DCMAKE_CXX_COMPILER=/c/msys64/ucrt64/bin/g++.exe \
  -DSR_BUILD_APP=OFF -DCMAKE_BUILD_TYPE=Debug
cmake --build build-gcc && ctest --test-dir build-gcc --timeout 60
```

为什么指明三处：`make` 在 MSYS2 的 **MSYS 环境**（`/c/msys64/usr/bin/`），`g++` 在 **UCRT64 环境**
（`/c/msys64/ucrt64/bin/`），不在同一个 PATH——生成器、make、编译器各指一次，CMake 才找得齐。
`SR_BUILD_APP=OFF` 关掉 Win32 app（选项 `CMakeLists.txt:14`，app 的门 `:175`）：C1′ 的承诺只到 core/loader/tests。
g++ 侧测试还加 `-static`（`:162-164`）——理由见坑 1。

**生产 harness 多了什么**：`.h`/`.cpp` 拆分（`tests/harness.cpp:10-15`），mini 的 inline-header 形式与之等价；`--only <子串>` 过滤
（`tests/harness.h:36-37`）——调试崩溃时手里只有半个用例名，敲错一个字母 = 一条没跑 = 看起来全绿，
所以"0 条匹配"必须判失败（`tests/harness.cpp:76-82`）；golden 路径注入 `SR_SOURCE_DIR`（`CMakeLists.txt:150-151`）
——CTest 的 cwd 是 `build/`，相对路径会把"找不到文件"误读成"没提交"（M3 笔记 §6）；CRT 硬化（`tests/main.cpp:25-31`）见坑 1。

### 计时器：为什么 `steady_clock` 能留在 core

`src/bench/timer.h:10-12`：设计文档提过 QueryPerformanceCounter，但 MSVC 上 `std::chrono::steady_clock`
的底层实现**就是** QPC，且不需要 `<windows.h>`——计时器因此能留在核心库里（C4）；要更高精度只需改这个头。
`elapsedMs()`（:23-26）读"距上次 restart"；`lapMs()`（:29-34）读一次时钟**并把起点重启在当下**。
分阶段计时用 lap：四阶段共用一只秒表，相邻 lap 首尾相接，求和 telescoping 成"最后一次 lap − 起点"，
四段**划分**一次 draw 的时间（`src/render/render_backend.cpp:42-44`、`:67`）。返回 double 而非 float：
一帧 16.67ms，float 的 7 位有效数字求平均会漂移（timer.h:21-22）。用仓库真头文件跑一遍（`-I` 指到 `src/`，两工具链实测）：

```cpp
#include <chrono>
#include <cstdio>
#include <thread>
#include "bench/timer.h"   // 直接用仓库里的生产头文件，-I 指到 src/
int main() {
    sr::Timer t;
    std::this_thread::sleep_for(std::chrono::milliseconds(2));
    const double lap1 = t.lapMs();      // 读时钟并把起点重启在当下
    std::this_thread::sleep_for(std::chrono::milliseconds(3));
    const double lap2 = t.lapMs();
    std::printf("lap1=%.3f ms  lap2=%.3f ms  elapsed-since-last-lap=%.3f ms\n",
                lap1, lap2, t.elapsedMs());
    return 0;
}
```

实测输出形如 `lap1=15.277 ms  lap2=15.276 ms  elapsed-since-last-lap=0.000 ms`。sleep 2ms 实测 7–25ms 不等，
是 Windows 计时/调度分辨率所致，别拿它当精度证据；要看的只是机制：第二次 lap 从第一次 lap 的时刻起算。
配套教训（`tests/unit/test_pipeline_integration.cpp:45-53`，Ruling 84 注释 + `drawUntilMeasured`）：计时断言跨机器可变，必须防抖（先把 draw
重复到足够长再判比值），否则在别人机器上闪红——**闪红的测试教会人忽略红，比没有测试更糟**（M6 账本 Ruling 84）。

### `$<CONFIG>`，而不是靠 NDEBUG 猜

`CMakeLists.txt:47-52` 注入 `SR_BUILD_CONFIG="$<CONFIG>"`。不用 `#ifdef NDEBUG` 的原因：多配置生成器下
**Release、MinSizeRel、RelWithDebInfo 都定义 NDEBUG**（实测生成的 vcxproj 三者皆有），靠它区分会把不同构建
标成同一个名字——而性能表与 golden 必须能归因到具体构建（`src/version.h:5-7`）。mini 实测：Debug 打印 `Debug`，
RelWithDebInfo 打印 `RelWithDebInfo`。`buildInfoString()` 用函数内 static string 拼一次（`src/version.cpp:34-36`）：
不在热路径，不值得为编译期拼接上 constexpr 字符串操作。

## 坑：三个真实吃掉调试时间的故障

### 坑 1：缺 DLL 不报错，CTest 记成 Timeout

Windows 上"缺 DLL"的表现**不是报错，是进程起不来**，CTest 记成 Timeout（M0 笔记 §7c）。本机 PATH 同时有
Git 的 mingw64 与 MSYS2 的 ucrt64，动态链接的 g++ 测试 exe 去找 `libstdc++-6.dll`，CTest 用 Windows PATH
起进程找不到——症状酷似"测试里死了循环"。修法：GNU 侧 `-static`（`CMakeLists.txt:157-164`）；纪律：
**`ctest` 一律带 `--timeout`**（README :33-34）——挂住的测试必须变成失败，否则一个误导性故障吃掉整个会话。
同族变体更隐蔽：M0 的悬垂指针触发 Debug CRT **模态对话框**，非交互会话没人能点，进程永久阻塞，同样只报 Timeout
（M0 笔记 §7b）；M5 发现未捕获异常 → abort 也弹框（M5 账本 Ruling 60）。修法不是 try/catch 接住继续跑（那会把红变绿），
而是关框 + 改道 stderr + 立即非零退出（`tests/main.cpp:16-31`）。**这一族的共同形状：故障被伪装成另一种故障。**

### 坑 2：退出码 256 = 全绿

`runAll()` 返回**失败用例数**（`tests/harness.cpp:107`），main 原样返回的话，POSIX 语义把退出码截断到
0–255：**恰好 256 条失败时退出码是 0**——一次让后面所有任务红/绿判读整体失效的灾难性回归，长得却像全绿。
M4 终审发现（deferred #8），M5.0 修复（commit `1fdf43f`），夹到 1：`tests/main.cpp:62-65`。
一行实验 `int main() { return 256; }`（两工具链实测）：bash 里 `$?` 是 **0**，cmd 里 `%ERRORLEVEL%` 是 256——
截断发生在 POSIX 层（bash、脚本、跨平台工具），Windows 本身保留完整值。夹到 1 之后退出码在任何调用方下都可读。

### 坑 3：静态库里的测试文件被静默丢掉

`SR_TEST` 生成的函数与 `Register` 对象全是**内部链接**，没有外部符号"需要"这个翻译单元；链接器从静态库
只拉**能解析未决符号**的 .obj——整个测试文件被丢掉，用例**一条都不跑，且不报任何错**。所以每个 `tests/unit/*.cpp`
都必须显式列进 `add_executable`（`CMakeLists.txt:86-88` 注释、`:92-147` 列表）。实测复现：下面的文件编成 .obj、
`lib` 打成静态库再链——`[run] 3 个用例`（第 4 条消失）；同一个 .obj 直接链——`[run] 4 个用例`。

```cpp
#include "harness.h"

// 这个文件会被做成静态库再链接——演示链接器把它整个丢掉。
SR_TEST(extra_case_from_static_lib) { SR_ASSERT(1 + 1 == 2); }
```
