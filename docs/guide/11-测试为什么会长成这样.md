# 11 — 测试为什么会长成这样

## 这一章要解决什么问题

前十章给了你出图、载入模型、光照与计时，每章末尾都有一条"你应该看到 X"。这一章问最后一个问题：
**你凭什么相信自己的绿？** 仓库此刻有 468 条用例——`./build/Debug/soft_raster_tests.exe` 末行打印
`[done] 468 个用例，失败 0 个`（HEAD `97a1499` 实测）。468 不是目标数字，是沉积物：几乎每一条都对应
一个真实发生过、或差点发生的错误。这一章讲清沉积的规律——四种失效模式，每种都在这个仓库里咬过人，
外加一条把它们串起来的证据链纪律。读完你写测试时会多一个动作：**先故意把实现改坏，确认测试会红，再改回来。**

## 片段 1：全绿不等于有判别力

同一份 8 像素图案、同一个改坏的实现，两种测试写法给出不同的红绿。单文件 `sym.cpp`，只用标准库：

```cpp
// guide11 片段 1 —— 对称夹具 vs 非对称断言（只用标准库，单文件）
#include <cstdio>
// 8 像素"贴图"：值单调 ⇒ 任何镜像/轴对调都会改变读数（数据本身非对称）。
static const int tex[8] = {0, 8, 16, 24, 32, 40, 48, 56};
// 被测实现：像素中心 u → 颜色。正确 = floor(u*8)；改坏 = 索引镜像（7-i）。
static int sampleRight(float u) { return tex[static_cast<int>(u * 8)]; }
static int sampleWrong(float u) { return tex[7 - static_cast<int>(u * 8)]; }
// 写法 A（对称采样）：只断言中心对 (3,4) 的均值。镜像把 3↔4 互换，均值不变。
static bool testSymmetric(int (*s)(float)) {
    return (s(0.4375f) + s(0.5625f)) / 2 == 28;   // (24+32)/2
}
// 写法 B（非对称采样）：钉住两个端点，镜像必然改变读数。
static bool testAsymmetric(int (*s)(float)) {
    return s(0.0625f) == 0 && s(0.9375f) == 56;
}
int main() {
    std::printf("[正确实现]     对称采样: %s   非对称采样: %s\n",
                testSymmetric(sampleRight) ? "绿" : "红",
                testAsymmetric(sampleRight) ? "绿" : "红");
    std::printf("[改坏实现镜像] 对称采样: %s   非对称采样: %s\n",
                testSymmetric(sampleWrong) ? "绿" : "红",
                testAsymmetric(sampleWrong) ? "绿" : "红");
    std::printf("[结论] 对称写法在实现改坏时仍绿：全绿 != 有判别力。\n");
    return 0;
}
```

`g++ -std=c++20 -Wall -Wextra sym.cpp -o sym && ./sym`（MSVC `cl /EHsc /std:c++20 /W4 sym.cpp` 同输出）：

```text
[正确实现]     对称采样: 绿   非对称采样: 绿
[改坏实现镜像] 对称采样: 绿   非对称采样: 红
[结论] 对称写法在实现改坏时仍绿：全绿 != 有判别力。
```

数据是非对称的，**断言**却可以是对称的：中心均值在镜像下不变，于是写法 A 对这个错误永远绿。
生产里的同款修复是 Ruling 36：纯棋盘格在转置下恒等，uv 轴对调永远红不起来，所以
`makeCheckerImage` 加三个角标记色，`assets/tga/checker.tga`（128×128）是**修复后的非对称版**
（M4 账本 `.superpowers/sdd/2026-11-21-soft-raster-m4-textures/progress.md:29-37`）。第 08 章片段 2 演过它的翻转版：对称纹理下四种翻转配置全同
（`docs/guide/08-OBJ与MTL导入.md:267`）。写插值/索引/采样/翻转类测试的固定一问：
**"把两个轴（或权重、取整、翻转）对调，我的夹具会给出不同的数吗？"**答"不会"就还没资格写断言
（`docs/notes/M5-OBJ导入与三次翻转.md:94-95`）。

## 片段 2：最小 harness 复刻，以及两个真实陷阱

生产的 harness 三件套：静态注册、断言记录不中断、退出码钳位。复刻它，然后亲手踩两个陷阱。
六个小文件（`mh.h`/`mh.cpp`/`main.cpp`/`main_raw.cpp`/`tu.cpp`/`t_fail.cpp`，另有一个生成文件）：

```cpp
// ---- mh.h ----
#pragma once
#include <cstdio>
#include <utility>
#include <vector>
using Fn = void (*)();
std::vector<std::pair<const char*, Fn>>& suite();
struct Register { Register(const char* n, Fn f); };
extern int g_fails;   // 当前用例内的失败数，runAll 每条用例前清零
// 比较经过函数而非常量 if：MSVC /W4 对常量条件报 C4127（生产 tests/harness.h:56-61 同款理由）
inline bool condIsFalse(bool v) { return !v; }
#define SR_TEST(name)                                                    \
    static void name();                                                  \
    static Register reg_##name(#name, &name);                            \
    static void name()
#define SR_ASSERT(c)                                                     \
    do { if (condIsFalse(static_cast<bool>(c))) { ++g_fails;             \
        std::printf("    FAIL %s:%d  %s\n", __FILE__, __LINE__, #c);     \
        std::fflush(stdout); } } while (0)   // 记录不中断：后面的断言继续跑
int runAll();
```

```cpp
// ---- mh.cpp ----
#include "mh.h"
int g_fails = 0;
std::vector<std::pair<const char*, Fn>>& suite() {
    static std::vector<std::pair<const char*, Fn>> s;
    return s;
}
Register::Register(const char* n, Fn f) { suite().emplace_back(n, f); }
int runAll() {
    int failed = 0;
    std::printf("[run] %d 个用例\n", static_cast<int>(suite().size()));
    for (const auto& e : suite()) {
        g_fails = 0;
        e.second();
        if (g_fails) { ++failed; std::printf("FAIL %s  (%d 处断言失败)\n", e.first, g_fails); }
    }
    std::printf("[done] %d 个用例，失败 %d 个\n", static_cast<int>(suite().size()), failed);
    return failed;
}
```

```cpp
// ---- main.cpp（钳位版）----
#include "mh.h"
int main() {
    const int failed = runAll();
    return failed > 1 ? 1 : failed;   // POSIX 退出码只有 0–255（生产 tests/main.cpp:62-65）
}
// ---- main_raw.cpp（未钳位对照，单独存一个文件）----
#include "mh.h"
int main() { return runAll(); }
// ---- tu.cpp（唯一一条用例，单独存一个文件）----
#include "mh.h"
SR_TEST(the_only_case) { SR_ASSERT(2 + 2 == 4); }
```

上面这个块为省行数合并展示了**三个独立文件**：`// ---- 文件名 ----` 是分隔标记，不是文件内容；
照标记拆成 `main.cpp`、`main_raw.cpp`、`tu.cpp` 各自保存（合在一个文件里会有三个 `main`，编不过）。
再写一个 `t_fail.cpp`：一条用例里两条假断言夹一条真断言，验证"记录不中断"：

```cpp
// ---- t_fail.cpp ----
#include "mh.h"
SR_TEST(record_not_abort) {
    SR_ASSERT(1 == 2);   // 第 1 处失败
    SR_ASSERT(3 == 4);   // 第 2 处失败仍被打印 ⇒ "记录不中断"的直接证据
    SR_ASSERT(5 == 5);   // 失败之后用例继续执行
}
```

256 条失败用例用命令生成，别手写：

```bash
{ echo '#include "mh.h"'; for i in $(seq 0 255); do echo "SR_TEST(f$i) { SR_ASSERT(false); }"; done; } > t256.cpp
g++ -std=c++20 -Wall -Wextra -c mh.cpp main.cpp main_raw.cpp tu.cpp t_fail.cpp t256.cpp
g++ mh.o tu.o main.o -o direct.exe        # 用例直接进 exe
ar rcs libtu.a tu.o                       # 同一个 tu.o 改放进静态库
g++ mh.o main.o libtu.a -o libdrop.exe    # 陷阱 (a)：链接器丢掉整个 TU
g++ mh.o t_fail.o main.o -o rec.exe
g++ mh.o t256.o main_raw.o -o raw256.exe  # 陷阱 (b)：失败数正好 256
g++ mh.o t256.o main.o -o clamp256.exe
```

MSVC 侧同形：`cl /EHsc /std:c++20 /W4 /c` 各文件，`lib /out:tu.lib tu.obj` 代替 `ar`，
`link mh.obj main.obj tu.lib /out:libdrop_msvc.exe` 代替第二条 `g++`。两侧零警告，输出逐字相同。
真跑结果（完整输出在 `build/guide-scratch-11/run_gpp.txt`、`run_msvc.txt`，gitignored）：

```text
direct.exe    [run] 1 个用例 → [done] 1 个用例，失败 0 个        退出码 0
libdrop.exe   [run] 0 个用例 → [done] 0 个用例，失败 0 个        退出码 0   ← 陷阱 (a)
rec.exe       两条 FAIL 行 + FAIL record_not_abort (2 处断言失败) 退出码 1
raw256.exe    [done] 256 个用例，失败 256 个   进程退出码 256，bash $? 读到 0 ← 陷阱 (b)
clamp256.exe  [done] 256 个用例，失败 256 个   退出码 1
```

（`rec.exe` 的 FAIL 行原文带"文件:行号"，指向 scratch 里的 `t_fail.cpp` 第 3/4 行；临时文件不进仓库，
引文摘要如上以免把临时文件当仓库引用。256 的进程退出码用 PowerShell `Start-Process -PassThru`
读到 `ExitCode=256`，bash 的 `$?` 是截断后的 0——两个读数都是真的，口径不同。）

- **陷阱 (a)：静态库丢 TU。** `tu.o` 里没有任何符号被 `main.o`/`mh.o` 引用——注册靠的是静态初始化，
  不是函数调用。链接器只从 `.a`/`.lib` 里拉"能解析未决符号"的成员，于是整个 TU 被丢掉，
  **一条不跑且不报错**，`[run] 0 个用例` 长得像全绿。这就是 `CMakeLists.txt:86-88` 那条注释的由来：
  每个测试 `.cpp` 必须显式列进 `add_executable`（列表在 `CMakeLists.txt:92-147`），不许图省事做成库。
- **陷阱 (b)：256 条失败 ⇒ 退出码 0。** POSIX 把退出码截断到 0–255，"退出码 = 失败用例数"
  在正好 256 时归零，后面所有任务的红绿判读整体失效。钳位 `failed > 1 ? 1 : failed`
  （生产 `tests/main.cpp:62-65`，M4 终审 deferred #8、M5.0 修复 `1fdf43f`）。
- **记录不中断**：`rec.exe` 打印了两条 FAIL 才汇总——第一条失败没杀死用例，第三条真断言也跑了。
  生产版还多一个动作：每条 FAIL 后 `fflush`（`tests/harness.cpp:20-24`）：重定向时 stdout 全缓冲，
  "断言失败后紧接着崩溃"会让 FAIL 行随进程消失，看起来像崩得毫无征兆。

## 指回本仓库：生产 harness 多了什么

片段 2 是骨架，生产版多出来的每一件都有对应的事故（`tests/harness.h`、`tests/harness.cpp`、`tests/main.cpp`）：

- **`--only <子串>` 过滤，0 匹配必须失败**（`tests/harness.cpp:76-82`）。拼错过滤器时
  "0 个用例，失败 0 个 → 退出码 0"比崩溃更难发现。用子串而非全名：调试时手里往往只有半个名字
  （`tests/harness.h:35-37`）；陌生参数与缺值 `--only` 都报错（`tests/harness.cpp:49-66`）。
- **数值断言一律容差**（`tests/harness.h:12-13`，C1′）：g++ 与 MSVC 的 sin/cos/pow 不保证逐位一致，
  精确相等会在换编译器时假性失败。整型断言失败打印两个值（`tests/harness.h:89-97`）——像素计数光看表达式没用。
- **CRT 硬化**（`tests/main.cpp:25-49`）：关 Debug CRT 模态框、terminate/SIGABRT 打印后 `_exit(3)`。
  不接住异常继续跑（那会把红变绿），只让缺陷信号**可见且快速失败**。模态框在非交互会话里永久阻塞，
  CTest 只报 Timeout——故障被伪装成另一种故障（第 00 章坑 1 同族）。
- **用例数本身是断言**：468 这个数随每次新增用例变化，`[run] N` 突然变小就是 TU 被丢的信号。
  本章片段 2 的陷阱 (a) 在仓库里发生过：第 00 章的 mini CMake 工程活体复现过它。

## 四种失效模式（每种都真实发生过）

### 1. 变异验证：断言必须"实现错着时会红"

写断言之前先问：**哪个错误会让它红？**答不出来的断言是装饰。做法是故意改坏实现（变异）、重跑、
要求红，且红必须是**断言级**而不是 abort——一次中止的变异运行不算证据（Ruling 57，
`docs/notes/M5-OBJ导入与三次翻转.md:96-97`）。真实案例：把 `src/render/render_backend.cpp:95` 的
`<=` 改成 `<`（平局语义反转），M3/M4 两份 golden **逐字节与基线相同**——凸立方体 + 背面剔除 ⇒
`depthRejected=0`，场景里不存在共面平局，该谓词在这个错误下根本不被触发（`docs/guide/README.md:78-82`
"06 深入"第 3 条）。平局语义由专门夹具钉住：`coplanar_triangles_last_writer_wins_because_comparison_is_less_or_equal`
（`tests/unit/test_depth.cpp:93`）。同一批复跑里的对照：删掉 `viewport.cpp:14` 的 `1.0f -`（y 翻转消失），
M3 立刻红 4674 像素，而覆盖/深度**计数器一个都不变**——计数对这类变异没有判别力，只有像素比对红
（`docs/guide/README.md:74-77`）。⇒ **±1 门守"重构没改变画面"，语义锚守"画面为什么对"，两者不可互替。**

### 2. 夹具对称性：夹具对目标错误对称就抓不到

片段 1 是它的最小形态。仓库里这一族的完整名单在 `docs/notes/M5-OBJ导入与三次翻转.md:74-81`
（M4 五行 + M5 双翻转第六行）。两个容易记错的真实细节：

- **checker.tga 不是反面教材，是修复后的样子。** 反面教材是"纯棋盘"：转置恒等、偶数 cells 下
  翻转也恒等（Ruling 36）。而"中心采样"的真实故事是 Ruling 41：格心在 level 0/1/2 上都是纯标记色，
  端到端**无法区分 bilinear 与 trilinear**——于是明说不装，mip 交给 LOD 单测 + golden 逐字节 + 肉眼
  "关 mip 会闪"（M4 账本 `.superpowers/sdd/2026-11-21-soft-raster-m4-textures/progress.md:64-70`）。
  不为"看起来全面"写恒真断言。
- **"断言对了结论、错在原因"**：M5.3 的 u16 夹具让字节数守卫先拒绝了它，删掉真正该守的 u16 守卫
  测试照样绿。修法是让夹具**只**触发目标守卫，并断言错误消息点名它（M5 notes:85-88）。
  一般化：凡"按 X 切换状态"的代码，对每一份状态做**交换**变异；置空/置零只证明"读了它"，
  不证明"读对了哪一个"（Ruling 67，M5 notes:89-92）。

### 3. 休眠接口：声明了没人读的字段不是中性的

**它是把 0 读成结论的陷阱**（`docs/notes/M6-光照与休眠接口.md:19-23`）。M3 留下的
`Varyings::worldNormal`/`worldPos` 没有任何 shader 读，`worldPos` 存着物体空间坐标却叫 world；
生产侧四处 `normalMatrix` 全是单位阵——包括带旋转的 golden 场景。正确的逆转置配方一直活在测试夹具里
（`tests/unit/test_pipeline_integration.cpp:26-28`），生产代码一处都没有（M6 notes:29-47）。
睡着的证据：把这两个字段语义改对，两份既有 golden **逐字节不变**（M6 notes:54-57）；
醒来的证据：lit 场景法线矩阵改回 identity ⇒ 比对红 2985 像素（M6 notes:60-62，破坏性验证 #13）。
三个后续案例：

- `ViewPlan::useFragmentShader`：P101 删掉它唯一的生产消费者后只剩测试读它 ⇒ 终审裁定删除
  （提交 `1d32d99`），用四帧 `cmp` 证明行为逐位不变（`build/m6_final_a4_identity.log`：
  phong/unlit/gouraud/lit 全 IDENTICAL）。现行形状与留痕见 `src/app/view_mode.h:22-27`。
- `fanTriangleCount`（`src/render/clipping.h:41`）：截至 HEAD 只有定义没有调用——
  `grep -rn fanTriangleCount src/ tests/` 只命中定义行。它还在仓库里，你可以自己跑这条 grep。
- 连注释也会休眠：`src/bench/timer.h:8` 自 M0 起承诺"用于 FrameStats 里的 ms* 字段"，
  而那些字段全仓库没人写，直到 M6.7 才成真（M6 notes:33-35）。**注释承诺了一件从未发生的事。**

### 4. 注释不许说代码没做的事

规则只有一条：**事实错误的注释比没有注释更危险**（Ruling 61，M5 账本
`.superpowers/sdd/2026-11-23-soft-raster-m5-obj/progress.md:422`）——
它阻止正确改动，而"这里有注释"让它看起来已被审过。本仓库抓出来并修掉的一族（引用前都重看过现状）：

| 假陈述 | 真相 | 修复提交 |
|---|---|---|
| `vec.h` 内侧法线 `{e.y,-e.x}` | top-down 屏幕里是 `{-e.y,e.x}`，符号相反（`src/math/vec.h:40-42`） | `d927025` |
| "正面是视觉 CW"（6 处 + 自称"权威"的测试注释） | 正面肉眼逆时针；权威是 `area2` 符号 + 语义 dot | `178e9db`、`a66fdfc` |
| M2 §5 拒绝顺序"退化→朝向→离屏" | 非有限→退化→**离屏**→朝向（`docs/notes/M2-几何阶段.md:78-79` 留痕） | `48d940f` |
| `sampler.h:4` "本文件目前只有 nearest" | 三种过滤都在（`src/render/sampler.h:4`） | `a3935b8` |
| sRGB `0.73` 属解码方向 | decode(0.5)≈0.214；0.73 是编码（`src/render/texture.h:31-34`） | `a3935b8` |
| 求逆阈值"与单位无关" | 只在大坐标端成立；小坐标端悬崖 s≈2.154e-3（`src/math/mat.h:166-169`） | `d927025` |

`a·a⁻¹` 那条注释（`src/math/mat.h:146-151`）是另一种形状：它记的是**症状如何把读者带偏**——
24 项展开抄错一个下标，`a*inv` 离单位阵差 0.2~0.9，看起来像精度问题、你会先去怀疑测试容差，
实际是索引错位（Ruling 16，M0–M3 账本 `.superpowers/sdd/2026-11-21-soft-raster-m0-m3/progress.md:167-171`）。
注释把真因钉住，读者才不至于绕路。
修代码时的配套纪律，四条缺一不可：**① 顺带让引用它的文档不变成新的假陈述**（回写必须带一次全文 grep，
只改评审点名的行等于把同一个错留在下一屏，Ruling 104）；**② 行数中性**（`git diff --numstat` 自检，
否则全系列的 `file:line` 引用漂移）；**③ 留痕**（不许悄悄改对，M2 notes:78 的"旧版此处写…"就是痕迹）；
**④ 引用写成命令而非孤立数字**（`docs/guide/README.md:94-96`，例：
`git rev-list --count 3f8cc2a..HEAD -- src/render src/scene`）。

## 证据链纪律：本章的落点

**一句"已验证"必须能映射到一个原始工件：命令 + 输出 + HEAD。**找不到就标"未验证"或删掉，
不许保留成声称（Ruling 107，M6 账本 `.superpowers/sdd/2026-11-25-soft-raster-m6-lighting/progress.md:626-635`）。
它诞生于一次具体的假复核：报告写"`tail -c 1` 复核为 `\n`"，而那次运行根本没发生。三条推论：

1. **中止的运行不算证据**（Ruling 57）：变异落在表外让 Debug CRT 直接 abort，拿不到"红了哪几条"。
2. **归因句先 grep 那个工件**（Ruling 113，同账本:851-865）：主控把自己编的话记成写手报告里的话，
   还讲给了产品方。"某工件说 X"入账前先 grep 该工件——事实错了会被测试撞穿，归因错了没人会去查。
3. **修声称的动作会生产新的未背书声称**（P115，同账本:672-678）：在"修 Ruling 107"那一轮里，
   新注释写"只改 msRaster 才崩"，而那个变异从未单独跑过。⇒ 每条声称配原始输出**本身也需要一道 grep**。

本会话真实发生过的失败，正是读者将来会犯的错（全部有账本出处）：

- **主控转述错 10 条以上**：批次三派发词被三个修复者合计驳回 10 条，每条附工件证据（Ruling 129，
  同账本:1045-1063）。其中"两个 HUD 矩形"是口径混淆的典型：账本写"HUD x<110 也不准"，

  `tests/unit/test_golden_scene_textured.cpp:373`）与 `x<110 && y<12`（`tests/unit/test_obj_golden.cpp:215`）。
- **闸门自己漏了后两章**：`citecheck.py` 原来 glob `docs/guide/0*.md`，从不覆盖 10/11 章；
  已改 `[0-9]*.md`（Ruling 134，同账本:1110-1121）。每批开工前先确认闸门能看见新文件。
- **代理声称交付而文件不存在**：10/11 两章写手 handback 都声称"已交付（347/338 行，含 ls/wc 自证）"，
  全盘 find 零命中（Ruling 134）。⇒ 写完立刻 `wc -l` + `ls -la` 自证；收 handback 第一件事是复核文件存在。

- **数字必须三件套**：窗口命令 + 实测值 + HEAD 短哈希（Ruling 129 硬门 5）。孤立数字会漂，
  命令不会；本章每个数字都给了产生命令或账本行号。
